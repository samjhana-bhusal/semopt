semopt / field guide

Cost-optimal query engine · plain-language tour

Ask an LLM a million questions — without paying a fortune.

semopt runs database-style queries where a language model answers each row, and makes them cheap by sending easy rows to a small model and only the hard ones to a big model — with a mathematical promise about how accurate the result will be.

01 · The problem

Why is this even hard?

Normal databases answer questions with fast, exact logic: WHERE price < 10 checks a number. But a lot of real data is unstructured — product reviews, support tickets, contracts, papers. To ask “does this review complain about shipping?” you need something that actually reads the text. That something is a large language model (LLM).

The catch: every LLM call costs money and time. Run the strongest model on 100,000 rows at about a cent each and one query costs $1,000. Do that for every question and the system is simply too expensive to use.

Background · what's an LLM call?

Think of it as renting a very smart reader by the word. You hand it some text and a question; it hands back an answer and a bill. Big models read better but charge much more. The whole game is: use the expensive reader as little as possible.

02 · The building blocks

Semantic operators: SQL, but the “where” clause is a sentence

semopt gives you a table you can run LLM-powered operations on. They look just like database operations, except the condition is written in plain English and judged by a model. There are five:

  • sem_filter — keep rows where a yes/no question is true (“is this a complaint?”)
  • sem_map — produce a new value per row (“summarize this in 5 words”)
  • sem_extract — pull structured fields out of messy text (clause type, risk level)
  • sem_join — match rows across two tables by meaning, not exact keys
  • sem_rank — order rows by how well they answer a query, keep the top-k
# Load a table, then filter it with an English predicate.
reviews  = SemanticTable.from_parquet("reviews.parquet")

complaints = reviews.sem_filter(
    "Does this review complain about shipping or packaging?",
    target_accuracy=0.90,   # ← you name the accuracy; semopt hits it
)

That target_accuracy is the whole personality of the project. You don’t fiddle with model choices or thresholds — you state the accuracy you need, and the engine figures out the cheapest way to deliver it. The next two sections are how.

03 · The big idea

The cascade: try cheap first, escalate only when unsure

Most rows are easy. “Great product, five stars!” obviously isn’t a shipping complaint — a tiny model nails it. So semopt runs a cascade: a small model tries first, and only when it isn’t confident does the row get escalated to a bigger, pricier model.

Tier 1 · cheap

Small local model

≈ free · runs on your laptop

Answers the easy majority. If it’s confident enough, we stop here and pay nothing.

Tier 2 · mid

Bigger local model

still ≈ free · slower

Catches the medium-hard rows the small model wasn’t sure about.

Tier 3 · expensive

Frontier API model

$$$ · the last resort

Only the genuinely hard rows reach here — a small slice of the total.

Background · “confidence”

When a model answers yes/no, it also reveals how sure it is (from the probabilities behind its answer). High sureness on an easy row; a coin-flip on a hard one. The cascade escalates whenever sureness drops below a threshold called τ (“tau”). The obvious question — where do you set τ? — is exactly what the guarantee answers.

Notice the tension: drag right and accuracy climbs but so does cost; drag left and it’s nearly free but sloppy. Every setting of τ is a different trade. The art is picking the τ that delivers exactly the accuracy you promised — no more (wasteful), no less (broken).

05 · The heart of it

The guarantee: how τ gets chosen, with a promise attached

A normal cascade (like the well-known “FrugalGPT”) picks τ by hand-tuning until it looks good. semopt’s contribution is to pick τ with conformal calibration — a statistics technique that turns “I hand-tuned it” into “I can prove the error rate stays at or below what you asked for.”

Background · conformal calibration in one breath

You set aside a small batch of examples where you know the right answers (the calibration set). You watch how confident the cheap model is exactly when it’s wrong. That tells you how high to set τ so that the wrong-but-accepted rows stay under your error budget α (alpha). The result isn’t a hunch — it’s a threshold with a finite-sample coverage guarantee.

Written as a promise: P(model is wrong AND we accepted it) ≤ α. If you ask for 90% accuracy, α is 0.10.

Here’s the payoff, measured on the project’s built-in test workload. The line you want to see is the blue one hugging the dotted diagonal: the accuracy you asked for (x-axis) matches the accuracy you actually got (y-axis), every time, inside a ±3% band.

This machinery was reused from the author’s earlier drift-detection project — the same weighted-conformal math, pointed at a new problem. That reuse is part of the research story.

06 · The other half

The optimizer: rewrite the query to spend less

The cascade makes each call cheaper. The optimizer makes fewer calls, by rewriting your query before it runs — the same way a database planner reorders work. You write the query naturally; it quietly improves it. Three moves do most of the work:

  • Reorder — run the cheapest, most selective filter first so it throws away rows before pricier steps see them.
  • Pushdown — slide filters ahead of expensive steps (like a per-row summarize) they don’t depend on, shrinking that step’s workload.
  • Memoize — spot duplicate rows and answer each unique one only once.

07 · Does it actually win?

Cheaper at the accuracy you asked for

The clinching picture is the cost–accuracy frontier. Every method is a point: further left is cheaper, higher up is more accurate. semopt’s blue line sits up and to the left of the alternatives — it delivers the target accuracy for less money.

The subtle win: the hand-tuned baseline (green diamond) is too cautious — it escalates more than needed and lands at 95% when you only wanted 90%, wasting money. semopt spends exactly enough to keep its promise, and not a cent more.

08 · Dive in

The codebase, in the order worth reading it

Everything lives under src/semopt/. Follow the numbered path and each file will make sense in terms of the one before it. Start at the table, end at the guarantee.

1table.pyThe front door. The SemanticTable you load data into and call .sem_filter() etc. on. Everything else hangs off this.
2operators/filter.pyOne operator, start to finish. Read this to see how a plain-English question becomes a per-row prompt and a kept/dropped decision. The other four operators mirror it.
3models/base.pyThe model interface. One tiny contract — .predict(prompt) — that local (MLX), API (OpenAI/Anthropic), and mock backends all satisfy.
4cascade/conformal.pyThe star. Turns a calibration set into the threshold τ with the coverage promise. If you read one file, read this.
5cascade/cascade.pyThe dispatcher. Sends each row down the tiers, stops when confident, records what happened. Uses τ from step 4.
6planner/optimizer.pyThe rewriter. The reorder / pushdown / memoize passes, each toggleable — that’s how the ablation chart is produced.
7experiments/run_coverage.pyProof, reproducible. Ties it together and prints the coverage table. Run it and watch the promise hold.
Supporting cast

cache/memo.py remembers answers so you never pay twice · cost/cost_model.py is the dollars-per-call source of truth · eval/ holds the metrics and the competing baselines · benchmarks/ defines the real datasets (stubbed — they need downloads + API keys).
